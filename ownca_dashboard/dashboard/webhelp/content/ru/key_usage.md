# Key Usage и Extended Key Usage

Эти расширения определяют, для чего можно использовать открытый ключ из
сертификата.

## Key Usage

Набор битов; каждый бит разрешает один вид операций.

| Бит | Название | Назначение |
|---|---|---|
| 0 | `digitalSignature` | Электронная подпись, кроме подписи сертификатов и CRL: установка соединения TLS, аутентификация, подпись данных. |
| 1 | `nonRepudiation` (`contentCommitment`) | Подпись, от которой владелец не может отказаться, — например, юридически значимая подпись документов. |
| 2 | `keyEncipherment` | Шифрование симметричного ключа при его передаче; применяется при обмене ключами RSA в TLS. |
| 3 | `dataEncipherment` | Шифрование данных непосредственно открытым ключом; на практике используется редко. |
| 4 | `keyAgreement` | Выработка общего секретного ключа (Диффи — Хеллман, ECDH, ГОСТ VKO). |
| 5 | `keyCertSign` | Подпись сертификатов. **Только для УЦ.** |
| 6 | `cRLSign` | Подпись CRL. **Только для УЦ или отдельного сертификата подписи CRL.** |
| 7 | `encipherOnly` | Уточнение к `keyAgreement`: только шифрование (имеет смысл, лишь если установлен `keyAgreement`). |
| 8 | `decipherOnly` | То же — только расшифрование. |

> RFC 5280 рекомендует помечать расширение Key Usage как критическое.

### Типичные сочетания

| Применение | Биты |
|---|---|
| Сервер TLS (RSA) | `digitalSignature`, `keyEncipherment` |
| Сервер TLS (ECDSA, ГОСТ) | `digitalSignature` (и `keyAgreement`) |
| Клиент TLS | `digitalSignature` |
| Подпись электронной почты (S/MIME) | `digitalSignature`, `nonRepudiation` |
| Шифрование электронной почты (S/MIME) | `keyEncipherment` |
| Подпись кода | `digitalSignature` |
| УЦ | `keyCertSign`, `cRLSign` |

## Extended Key Usage

Список OID, определяющих назначение сертификата. В отличие от Key Usage,
EKU обычно не помечается как критическое, но программы (особенно браузеры
при проверке сертификата сервера) проверяют его обязательно.

### Распространённые OID

| OID | Название | Назначение |
|---|---|---|
| `1.3.6.1.5.5.7.3.1` | `id-kp-serverAuth` | Аутентификация сервера TLS |
| `1.3.6.1.5.5.7.3.2` | `id-kp-clientAuth` | Аутентификация клиента TLS |
| `1.3.6.1.5.5.7.3.3` | `id-kp-codeSigning` | Подпись кода |
| `1.3.6.1.5.5.7.3.4` | `id-kp-emailProtection` | Защита электронной почты (S/MIME) |
| `1.3.6.1.5.5.7.3.8` | `id-kp-timeStamping` | Служба меток времени |
| `1.3.6.1.5.5.7.3.9` | `id-kp-OCSPSigning` | Подпись ответов OCSP |
| `2.5.29.37.0` | `anyExtendedKeyUsage` | Любое назначение |
| `1.3.6.1.4.1.311.10.3.4` | Microsoft EFS | Шифрование файлов |
| `1.2.643.2.2.34.6` | ГОСТ — сервер TLS | Применяется в сертификатах для российских систем |

### Как проверяются Key Usage и EKU вместе

При проверке цепочки программа требует, чтобы оба расширения разрешали
нужное применение. Например:

* для сервера TLS Key Usage должен включать `digitalSignature`, а EKU —
  `serverAuth`;
* если EKU есть, но `serverAuth` в нём нет, сертификат **не будет принят**
  как сертификат сервера, каким бы ни был Key Usage.

## Где это настраивается в OwnCA

В каждом [профиле сертификата](cert_profiles.md) — флажки Key Usage и
список EKU. Если в форме [Выпуск сертификата](custom_cert_issue.md) выбран
профиль, Key Usage и EKU берутся из него, а флажки и список EKU в форме не
учитываются. Если профиль Key Usage или EKU не задаёт, используется
значение из формы. В свободном режиме (без профиля) используются значения
формы.
