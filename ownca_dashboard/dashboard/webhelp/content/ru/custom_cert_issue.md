# Выпуск сертификата

Страница `/custom-cert-issue/` (пункт меню **Выпуск сертификата**).
Сертификат выпускается сразу, без заявки и её согласования: выберите УЦ и
профиль, заполните нужные поля и нажмите **Выпустить сертификат**. После
выпуска откроется страница нового сертификата.

По умолчанию профиль **обязателен**. Чтобы выпускать сертификаты без
профиля (в свободном режиме), включите переключатель **Разрешить выпуск
без профиля** на странице [Конфигурация](configuration.md).

## Когда нужен свободный режим

* Тестовые и служебные сертификаты с необычным набором расширений, для
  которых не хочется заводить отдельный профиль.
* Сертификат с новым OID, которого ещё нет ни в одном профиле.
* Проверка поведения программ — например, как приложение отнесётся к
  определённому `keyUsage` вместе с критическим `policyConstraints`.

## Поля формы

| Раздел | Что задаётся |
|---|---|
| **Издатель (УЦ)** | УЦ, который подпишет сертификат (обязательно). |
| **Профиль** | При выборе профиля подставляются его KU, EKU и расширения и появляются поля для значений OID из профиля. Вариант «Свободный (без профиля)» есть, только если выпуск без профиля разрешён в конфигурации. |
| **Ключ и срок действия** | Алгоритм ключа (`gost2012_256`, RSA, ECDSA и др.); для ГОСТ появляется выбор набора параметров. Срок действия в днях. В списке только алгоритмы, совместимые с выбранным УЦ (см. ниже). |
| **Субъект** | Общее имя (CN, обязательно), страна, регион, город, организация, подразделение. |
| **Альтернативные имена субъекта** | DNS-имена, IP-адреса, адреса электронной почты, URI, otherName — по одному значению в строке. |
| **Использование ключа** | По флажку на каждый бит Key Usage и признак критичности. Используется в свободном режиме; если Key Usage задан в профиле, флажки не учитываются. |
| **Расширенное использование ключа** | Список назначений (`serverAuth, clientAuth, …`) и признак критичности; правило то же. |
| **Точки распространения** | `crl_url`, `aia_url`, `ocsp_url`, `sia_url`, `freshest_crl_url`; незаполненные берутся из УЦ. |
| **Идентификаторы ключа** | Включение `subjectKeyIdentifier`, `authorityKeyIdentifier` и `issuer:always` для AKI. |
| **Значения кастомных OID** | В свободном режиме — строки вида *(OID, тип ASN.1, значение)*; при выборе профиля — обязательные поля для OID из профиля. |
| **Дополнительные строки расширений openssl** | Произвольные строки, которые добавляются к расширениям сертификата без изменений. |
| **Внешний CSR** | Загрузка запроса в PEM (или вставка его текста). Если запрос указан, сервер подписывает его, а новый ключ не создаётся. |

### Совместимость ключей УЦ и сертификата

УЦ подписывает только сертификаты, ключ которых относится **к тому же
семейству**, что и ключ самого УЦ:

| Семейство | Алгоритмы |
|---|---|
| `gost` | `gost2012_256`, `gost2012_512` |
| `rsa` | `rsa:2048`, `rsa:4096` |
| `ec` | `ec:P-256`, `ec:P-384` |
| `ed25519` | `ed25519` |

После выбора УЦ в списке **Алгоритм** остаются только алгоритмы его
семейства; если ранее выбранный алгоритм не подходит, вместо него
выбирается первый подходящий. Сервер повторяет эту проверку при отправке
формы: запрос с несовместимым алгоритмом отклоняется с сообщением
*«Key algorithm … is not compatible with the issuing CA»*, и сертификат не
выпускается.

Если приложен внешний запрос, семейство определяется **по открытому ключу
из запроса**, а не по списку в форме: список мог остаться от разбора
другого файла. Учитывается только открытый ключ, алгоритм подписи запроса
значения не имеет. Несовпадение отклоняется до выпуска, поэтому запрос с
ключом RSA нельзя подписать ключом ГОСТ-УЦ, и наоборот. Кнопка
**Прочитать CSR** сообщает о несовпадении сразу, ещё до отправки формы.

Сертификат подчинённого УЦ подписывает родительский УЦ, поэтому то же
правило действует и при создании подчинённого УЦ на странице
[Управление УЦ](cas.md).

### Как сочетаются профиль и поля формы

Если профиль выбран, за основу берутся его расширения. Расширение из полей
формы добавляется, только если в профиле такого расширения **нет**.
Например, если профиль задаёт `keyUsage`, флажки Key Usage в форме его не
дополнят, а расширения, которых в профиле нет, берутся из формы.

Для адресов, которые задаются и в УЦ (CDP, AIA, OCSP, SIA, freshestCRL,
issuerAltName), действует порядок: значение профиля, затем значение УЦ;
если оба пусты, расширение не добавляется.

## Что происходит при выпуске

1. Поля формы объединяются с выбранным профилем в итоговый набор
   расширений.
2. Проверяется, заполнены ли обязательные поля OID из профиля.
3. Выпускающий УЦ подписывает сертификат.
4. Открывается страница сертификата, где можно скачать сертификат, ключ,
   запрос, PEM-файл или файл PKCS#12.
