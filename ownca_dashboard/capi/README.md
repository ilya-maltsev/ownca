# `ownca_capi` — обёртка на C над CryptoPro CSP (CAPILite)

Небольшая программа на C, через которую OwnCA выполняет все ГОСТ-операции УЦ
при включённом CryptoPro CSP. Python запускает её как отдельный процесс
(`subprocess`) — так же, как запускает `openssl`. Ключ УЦ никогда не покидает
контейнер CryptoPro: между процессами передаются только сертификаты, CRL и
файлы PFX в кодировке DER.

Исходный код: [`ownca_capi.c`](ownca_capi.c) (один файл, зависит только от
CAPILite). Вызывающий код: [`../dashboard/own_ca.py`](../dashboard/own_ca.py).

**Зачем отдельный процесс.** Ключ хранится в контейнере CryptoPro, и Python
не должен иметь к нему доступа — это гарантирует само разделение процессов, а
не договорённость в коде. Кроме того, совмещать OpenSSL и CAPILite в одном
процессе ненадёжно: у них разное представление ключей, разные кодировщики
ASN.1 и разная запись DN. Наконец, `own_ca.py` и раньше вызывал
`subprocess.run(['openssl', …])`, и обёртка вписалась в ту же схему:
`_run_capi()` отличается от `_run()` только именем исполняемого файла.

Отсюда главное правило: **обёртка не принимает решений о том, что можно
выпускать**. Она ничего не знает о профилях, режимах выпуска и правах
пользователя — всё это проверяется в Python до вызова.

---

## 1. Сборка

Обёртка собирается только в образе, в который устанавливается дистрибутив
CryptoPro (см. [`dev_env/build.sh`](../../dev_env/build.sh)). Команда сборки
приведена в [`dev_env/dashboard/Dockerfile`](../../dev_env/dashboard/Dockerfile):

```sh
gcc -DUNIX -DHAVE_LIMITS_H -m64 -DSIZEOF_VOID_P=8 \
    -I/opt/cprocsp/include -I/opt/cprocsp/include/cpcsp \
    -I/opt/cprocsp/include/asn1c/rtsrc -I/opt/cprocsp/include/asn1data \
    ownca_capi.c -o /opt/ownca/bin/ownca_capi \
    -L/opt/cprocsp/lib/amd64 -lssp -lcapi10 -lcapi20 -lrdrsup
```

Ключи `-DUNIX -DHAVE_LIMITS_H -DSIZEOF_VOID_P=8` обязательны: без них
заголовочные файлы CryptoPro подставляют типы для Windows. Компилятор `gcc`
устанавливается только на время сборки и затем удаляется. После успешной
сборки создаётся файл-признак `/opt/ownca/.cryptopro_available`; его
проверяет `cryptopro.available()`, и без него CryptoPro считается
недоступным.

**Пересборка при отладке.** Каталог `ownca_dashboard/` подключён в контейнер,
поэтому обёртку можно перекомпилировать на месте, не пересобирая образ:
установите в контейнер `gcc libc6-dev` и выполните приведённую выше команду
для `/opt/app/capi/ownca_capi.c`. Так удобно проверять изменения, но
окончательный вариант обязательно соберите заново полностью
(`dev_env/build.sh`): иначе первый же `docker compose up --force-recreate`
вернёт исполняемый файл из образа, и изменения пропадут.

## 2. Порядок вызова

| | |
|---|---|
| **Успех** | код возврата `0`, одна строка JSON в `stdout` |
| **Ошибка выполнения** | код `1`, описание ошибки в `stderr` |
| **Ошибка в аргументах** | код `2`, подсказка по использованию в `stderr` |

Функция `_run_capi` считает ненулевой код ошибкой и возбуждает `OwnCAError`
с текстом из `stderr` и `stdout`. Это сообщение пользователь видит в панели
без изменений, поэтому пишите его понятно не только для разработчика.

JSON выводится **последней строкой**: вызывающий код разбирает
`out.strip().splitlines()[-1]`. Ничего не выводите после него.

Все команды, создающие файл, принимают `--out FILE` и записывают его в
кодировке **DER**. В PEM файл переводит Python (`_der_file_to_pem`): это
простое перекодирование в base64, OpenSSL для ГОСТ-данных при этом не
вызывается.

## 3. Команды

```
ownca_capi <info|paramsets|genkey|gencsr|selfsign|issue|issuecsr|gencrl|exportpfx|importpfx|delcontainer> [параметры]
```

### `info`
Проверка работоспособности, без параметров → `{"shim":"ownca_capi","ok":true}`.

### `paramsets --alg gost2012_256|gost2012_512`
Наборы параметров, поддерживаемые установленным CryptoPro
(`PP_ENUM_SIGNATUREOID`). Нужны, чтобы форма выпуска не предлагала набор,
который CryptoPro отвергнет.
→ `{"alg":"gost2012_256","oids":["1.2.643.2.2.35.1", …],"ok":true}`

### `genkey --container ИМЯ [--alg ...] [--paramset A|B|C|XA|XB]`
Создаёт в контейнере ключевую пару `AT_SIGNATURE`. Признак `CRYPT_EXPORTABLE`
обязателен: без него `PFXExportCertStoreEx` без какой-либо ошибки создаст PFX
без ключа.

Набор параметров задаётся **до генерации ключа**
(`CryptSetProvParam(PP_SIGNATUREOID)`, затем `CryptGenKey`). Описанный в
документации способ с отложенной генерацией (`CRYPT_PREGEN` +
`KP_SIGNATUREOID` + `KP_X`) для `AT_SIGNATURE` в этой версии CryptoPro не
работает — см. раздел 7. Неизвестное имя набора отклоняется с кодом `2`, и
контейнер не создаётся. Если ключ уже существует (`NTE_EXISTS`), команда
завершается успешно и ничего не меняет, поэтому её можно вызывать повторно.

### `gencsr --container ИМЯ --subject DN [--alg ...] --out FILE`
Запрос PKCS#10 для ключа из контейнера, подписанный этим же ключом. Для
выпуска сертификата команда не нужна (`issue` берёт открытый ключ прямо из
контейнера): она нужна, чтобы у сертификата с ключом, созданным на сервере, на
диске был такой же `csr.pem`, как при работе через OpenSSL. Ошибка этой
команды выпуск не прерывает: если обёртка старой версии и команды не знает,
сертификат всё равно выпускается.

### `selfsign --container ИМЯ --subject DN --out FILE [--days N] [--serial HEX] [--alg ...] [--extspec FILE]`
Самоподписанный сертификат корневого УЦ. По умолчанию `--days 3650`.

### `issue --container CA --subject-container SUBJ --subject DN --issuer DN --out FILE [--days N] [--serial HEX] [--alg CA_ALG] [--subject-alg SUBJ_ALG] [--extspec FILE]`
Выпуск сертификата для ключа из контейнера владельца: подчинённого УЦ или
конечного сертификата с ключом, созданным на сервере. По умолчанию
`--days 365`. `--alg` — алгоритм **УЦ** (от него зависят OID подписи и тип
криптопровайдера), `--subject-alg` — алгоритм ключа владельца; они могут
различаться (256 и 512 бит).

### `issuecsr --container CA --csr FILE --issuer DN --out FILE [--subject DN] [--days N] [--serial HEX] [--alg CA_ALG] [--extspec FILE]`
Выпуск по внешнему запросу PKCS#10 (DER): запрос декодируется, **его подпись
проверяется** криптопровайдером, выбранным по алгоритму ключа из самого
запроса (а не по алгоритму УЦ), затем сертификат подписывается ключом УЦ.

По умолчанию Subject DN копируется из запроса **байт в байт** — это нужно,
чтобы цепочка сертификатов проверялась без расхождений; параметр `--subject`
заменяет его. Собственных правил формирования DN у обёртки нет: OwnCA
составляет DN по правилам УЦ (как `openssl ca` по `[ policy_default ]`) и
передаёт `--subject`, когда результат отличается от DN запроса.

### `gencrl --container CA --issuer DN --out FILE [--days N] [--crlnumber HEX] [--revoked FILE] [--alg ...]`
Подпись CRL ключом УЦ. По умолчанию `--days 7`, но Python всегда передаёт
значение явно (`_ca_crl_days`). Время `thisUpdate` ставится на 5 минут раньше
текущего — с запасом на расхождение часов у проверяющей стороны. Формат
`--revoked` описан в разделе 5.

**При любой ошибке CRL не подписывается** (код возврата 1): если файл
отозванных сертификатов не открывается, строку в нём не удаётся разобрать
(серийный номер, время, код причины 0–10), строка слишком длинная или не
хватило памяти. Пропуск строки означал бы, что отозванный сертификат исчез из
CRL. Число записей не ограничено. Python проверяет файл по тем же правилам до
вызова (`own_ca._check_revoked_index`).

### `exportpfx --container ИМЯ --cert FILE [--password PW | --password-stdin] [--chain FILE]... [--alg ...] --out FILE`
Упаковывает сертификат и ключ из контейнера в PFX (`PFXExportCertStoreEx`).
Параметр `--chain` можно указывать несколько раз; он добавляет сертификаты
**без ключей** (родительские УЦ). Контейнер шифруется так, как это по
умолчанию делает CryptoPro, и изменить это нельзя: `pvReserved`
зарезервирован, набор `dwFlags` фиксирован. Поэтому ни формат ТК 26, ни
ГОСТ-алгоритмы шифрования по паролю здесь недоступны.

**Пароль.** `--password-stdin` читает пароль из первой строки стандартного
ввода и имеет приоритет над `--password`. OwnCA передаёт пароль только так:
аргументы командной строки видны любому процессу в контейнере через
`/proc/<pid>/cmdline`. Параметр `--password` оставлен для ручной проверки.
Строка без завершающего перевода строки или длиннее 1024 байт считается
ошибкой (код 2) — пароль не обрезается. Python ещё до вызова отклоняет пароль
длиннее 32 символов или содержащий символы CR, LF, NUL
(`own_ca.check_pfx_password`); поле ввода ограничено той же длиной.

### `importpfx --pfx FILE [--password PW | --password-stdin] --out FILE`
`PFXIsPFXBlob` → `PFXVerifyPassword` → `PFXImportCertStore`. Закрытый ключ
сразу помещается в контейнер и на диск не попадает; в `--out` записывается
сертификат, которому принадлежит ключ (DER).

```json
{"out":"...","container":"pfx-<guid>","provtype":80,"subject":"CN=..., O=...","ok":true}
```

Имя контейнера **назначает CryptoPro**. Python обязан сохранить его из этого
ответа (`cas/<uuid>/backend`) — вычислить его по своему шаблону нельзя.

### `delcontainer --container ИМЯ [--alg ...]`
Удаляет контейнер ключа (`CryptAcquireContextA(..., CRYPT_DELETEKEYSET)`).
Вызывается при удалении УЦ или сертификата, а также при неудачном создании:
каталог на диске удаляет `shutil.rmtree`, но ключ хранится в хранилище
CryptoPro, вне тома с данными.

```json
{"container":"ownca_ca_...","provtype":80,"deleted":true,"ok":true}
```

Контейнер определяется не только именем, но и типом криптопровайдера, а тип
импортированного контейнера выбирает `PFXImportCertStore`. Поэтому `--alg` —
лишь подсказка: обёртка пробует оба типа ГОСТ. Если контейнера нет
(`NTE_BAD_KEYSET`), возвращается `deleted:false` с кодом 0: удаление
вызывается и там, где контейнер мог быть не создан, и повторный вызов не
должен приводить к ошибке. После успешного удаления дескриптор
недействителен, освобождать его нельзя.

## 4. Формат `extspec`

Текстовый файл со строками `ключ=значение`; строки, начинающиеся с `#`, —
комментарии. Неизвестные ключи пропускаются без предупреждения: поэтому
новые ключи не ломают старые версии, но и опечатка в имени ключа ничем не
выдаёт себя. Сверяйтесь со значением `ext=N` в ответе — это число
действительно добавленных расширений. Повторяющиеся ключи накапливаются (не
больше `MAX_LIST` = 32 значений), всего расширений — не больше `MAX_EXT` = 16.

| Ключ | Значение | Расширение |
|---|---|---|
| `bc` | `1` — добавить | basicConstraints |
| `bc_ca` | `0`/`1` | `CA:` |
| `bc_critical` | `0`/`1` | признак критичности |
| `bc_pathlen` | целое; `<0` — не задавать | `pathlen:` |
| `ku_hex` | биты KeyUsage, шестнадцатеричное число | keyUsage |
| `ku_unused` | число неиспользуемых битов в последнем байте | |
| `ku_critical` | `0`/`1` | |
| `eku` | OID; **можно повторять** | extendedKeyUsage |
| `eku_critical` | `0`/`1` | |
| `ski` | `1` | subjectKeyIdentifier (ГОСТ-хеш открытого ключа) |
| `aki` | `1` | authorityKeyIdentifier (keyid = SKI ключа УЦ) |
| `aki_issuer_dn` | DN в формате X.500 | authorityCertIssuer (directoryName) |
| `aki_issuer_serial` | шестнадцатеричное число | authorityCertSerialNumber |
| `san_dns` `san_email` `san_uri` | значение; можно повторять | subjectAltName |
| `san_ip` | **байты адреса в шестнадцатеричном виде**, не через точку; можно повторять | |
| `cdp` | URI; можно повторять | crlDistributionPoints |
| `aia_ca` / `aia_ocsp` | URI; можно повторять | AIA: caIssuers / OCSP |
| `sia_repo` | URI; можно повторять | subjectInfoAccess, caRepository |
| `freshest_crl` | URI; можно повторять | freshestCRL |
| `ian_dns` `ian_email` `ian_uri` `ian_ip` | как `san_*` | issuerAltName |

Ключи `aki_issuer_*` действуют только вместе с `aki=1`. Они соответствуют
записи OpenSSL `authorityKeyIdentifier = keyid:always, issuer:always` и
указывают на **сертификат УЦ**: DN его издателя и его серийный номер.

Пример для подчинённого УЦ со всеми адресами:

```
bc=1
bc_ca=1
bc_critical=1
bc_pathlen=0
ku_hex=06
ku_unused=1
ku_critical=1
ski=1
aki=1
cdp=http://pki.example/root.crl
aia_ca=http://pki.example/root.crt
aia_ocsp=http://ocsp.example/
sia_repo=http://pki.example/repo/
freshest_crl=http://pki.example/delta.crl
ian_dns=ca.example
ian_ip=0a000001
```

## 5. Формат `--revoked`

Одна строка на отозванный сертификат: `serialhex[,unixtime[,reasoncode]]`.
Здесь `serialhex` — серийный номер в шестнадцатеричном виде (чётное число
цифр, старший байт первым), `unixtime` — время отзыва (по умолчанию текущее),
`reasoncode` — код причины по RFC 5280, п. 5.3.1 (`1` — keyCompromise,
`4` — superseded и т. д.).

**Если третьего поля нет, причина считается не указанной**, и расширение
`reasonCode` не добавляется. Так же поступает OpenSSL при отзыве без
`-crl_reason`: если пользователь причину не указал, подставлять за него
`unspecified` не следует. Строки с `#` и нераспознанные серийные номера
пропускаются.

## 6. Представление данных

**Серийные номера.** На входе — шестнадцатеричная запись, старший байт
первым; `parse_serial_le` переставляет байты в обратном порядке, потому что
`CRYPT_INTEGER_BLOB` в CryptoAPI хранит младший байт первым. Python создаёт
серийный номер положительным (старший бит сброшен) и ненулевым.

**DN.** Разбирается функцией `CertStrToNameA` с `CERT_X500_NAME_STR`, то есть
в виде `CN=x, O=y`. Запись OpenSSL `/CN=x/O=y` **не принимается** — Python
преобразует её (`own_ca._openssl_subj_to_x500`), заключая каждое значение в
кавычки и удваивая кавычки внутри: `O="Acme, CN=Administrator"`. Без кавычек
запятая в значении превратилась бы в лишний атрибут DN подписанного
сертификата. DN с переводом строки или символом NUL отклоняется. Чтобы
цепочка проверялась без расхождений, точная строка DN сохраняется на диск при
создании УЦ (`subject_x500`, `issuer_x500`), а не восстанавливается из
сертификата.

**Имена контейнеров.** Контейнеры, созданные OwnCA, называются
`ownca_ca_<hex>` и `ownca_crt_<hex>` (без дефисов — хранилище HDIMAGE их не
поддерживает). Импортированные контейнеры называет CryptoPro. Имя контейнера
всегда берётся из файла `cas/<uuid>/backend`, а не вычисляется по шаблону.

**Алгоритмы.** `gost2012_256` — криптопровайдер типа 80, `gost2012_512` —
типа 81. От этого зависят OID подписи, хеш-функция для SKI/AKI и список
доступных наборов параметров.

**Что остаётся в Python** (и **не** должно переноситься в C): проверка наличия
CryptoPro по файлу-признаку, проверка набора параметров по списку CryptoPro,
отказ при неподдерживаемых расширениях (`capilite_unsupported_ext_keys` —
единый список и для отказа, и для предупреждения в интерфейсе), разбор
`issuerAltName` по типам, перевод DER в PEM, счётчик CRL, хранение сведений
об УЦ.

## 7. Ошибки, встречавшиеся на практике

| Код | Имя | Причина |
|---|---|---|
| `0x80090022` | `NTE_SILENT_CONTEXT` | Закончилась гамма ДСЧ: CryptoPro пытается запросить случайные данные через диалоговое окно, а сеанс открыт в режиме `CRYPT_SILENT`. Загрузите гамму на странице «Обслуживание». |
| `0x80090009` | `NTE_BAD_FLAGS` | `CryptGenKey` с `CRYPT_PREGEN` для `AT_SIGNATURE`: отложенная генерация в этой версии CryptoPro не поддерживается — набор параметров задаётся через `PP_SIGNATUREOID` до генерации. |
| `0x8009000A` | `NTE_BAD_TYPE` | `CryptSetKeyParam(KP_SIGNATUREOID)` для уже созданного ключа: параметры выбираются до генерации. |
| `NTE_EXISTS` | | В контейнере уже есть ключ. `genkey` считает это успехом. |

## 8. Доработка и проверка

**Как добавить расширение X.509.** Добавьте поле в `ExtSpec` и его разбор в
`parse_extspec` (имя ключа не должно начинаться так же, как существующие);
затем блок кодирования в `build_extensions` по образцу соседних (следите за
`MAX_EXT`) и освобождение памяти (`rgExt[i].Value.pbData` освобождает
вызывающая функция, промежуточные буферы — тот же блок). В Python добавьте
параметр в `_write_extspec`, передачу значения из `CertSpec`/`CASpec` и
**уберите ключ из списка отказа** `_CAPI_SUPPORTED_EXT_KEYS`. Напишите тест
на строку `extspec` и проверьте результат на установленном CryptoPro.

**Как добавить команду.** Функция `cmd_*` рядом с похожими (порядок важен:
статические функции должны быть определены до использования), строка в
`main`, строка в `usage` и описание в комментарии в начале файла.

**Не переносите** в обёртку правила выпуска и значения по умолчанию, которые
уже есть в Python: две копии одной логики рано или поздно разойдутся, и
этого никто не заметит.

**Проверка.** Тесты Python (`dashboard/tests/test_cryptopro.py`) **заменяют**
вызовы обёртки заглушками: они проверяют передаваемые параметры и разбор
ответа, но не сам CAPILite, — тесты должны проходить и на образе без
CryptoPro. Поэтому код на C проверяется вручную на образе с CryptoPro:

```sh
D='docker compose -f dev_env/docker-compose.yml exec -T gh_ownca_dev_dashboard'
# гамма (иначе NTE_SILENT_CONTEXT)
$D python -c "
import django,os; os.environ.setdefault('DJANGO_SETTINGS_MODULE','config.settings'); django.setup()
from dashboard import cryptopro; cryptopro.write_gamma(cryptopro.generate_gamma(500), mode='replace')"

$D sh -lc '
set -e
W=/tmp/chk; rm -rf $W; mkdir -p $W
printf "bc=1\nbc_ca=1\nbc_critical=1\nku_hex=06\nku_unused=1\nku_critical=1\nski=1\naki=1\n" > $W/ext.txt
/opt/ownca/bin/ownca_capi genkey  --container chk_ca --alg gost2012_256 --paramset A
/opt/ownca/bin/ownca_capi selfsign --container chk_ca --subject "CN=Chk CA, O=OwnCA" \
    --days 365 --serial 4011223344556677 --alg gost2012_256 --extspec $W/ext.txt --out $W/ca.der
openssl x509 -inform DER -in $W/ca.der -noout -text | head -30
/opt/cprocsp/bin/amd64/csptest -keyset -deletekeyset -container chk_ca'
```

Результат проверяйте **независимыми средствами** (`openssl x509 -text`,
`openssl crl -text`, `openssl req -verify`), а не по ответу обёртки:
`{"ok":true}` означает лишь, что CAPILite не вернул ошибку, но не то, что
закодировано именно то, что нужно. После проверки удаляйте контейнеры: они
сохраняются и после пересборки образа, потому что `/var/opt/cprocsp/keys`
находится в отдельном томе.

## 9. Ограничения

Полный перечень — во встроенной справке (**Система → Криптопровайдер
CryptoPro CSP**) и в [корневом README](../../README.md#ограничения-криптопровайдера-cryptopro).
Кратко:

* алгоритм шифрования PFX выбрать нельзя — используется шифрование CryptoPro
  по умолчанию;
* обёртка кодирует только расширения из таблицы в разделе 4; сертификат с
  любым другим расширением Python отклоняет ещё **до** вызова обёртки;
* `otherName` в SAN и `dirName`/`RID` в issuerAltName не поддерживаются;
* закрытый ключ можно получить только в составе PFX.
