# OwnCA

**Русский** | [English](README.en.md)

---

Веб-панель удостоверяющего центра. Заменяет самодельные сценарии на основе
EasyRSA и `openssl ca`: создаёт корневые и подчинённые УЦ, выпускает и
отзывает сертификаты X.509, своевременно обновляет списки отзыва (CRL),
выгружает ключи и сертификаты в PEM и PKCS#12 — всё это через браузер, а не
в терминале.

Работает на стандартном OpenSSL с алгоритмами RSA, ECDSA и Ed25519. Поддержка
ГОСТ Р 34.10-2012 включается отдельно; без неё OwnCA — обычный УЦ на
стандартном OpenSSL без дополнительных модулей. Если требуется
сертифицированная криптография, ГОСТ-операции можно выполнять средствами
CryptoPro CSP.

## Возможности

- **Удостоверяющие центры.** Создание корневых и подчинённых УЦ: генерация
  ключа, самоподписанный сертификат корня, подпись сертификата подчинённого УЦ
  родительским. Импорт существующего УЦ — сертификата с закрытым ключом или
  контейнера PKCS#12/PFX — чтобы продолжить выпуск от его имени. Задаются
  алгоритм ключа, Subject DN, срок действия и длина цепочки (`pathlen`).
  Подчинённый УЦ использует то же семейство ключей, что и родительский: ГОСТ и
  RSA в одной цепочке не смешиваются.
- **Выпуск сертификатов.** Ключ генерируется на сервере или поступает вместе с
  внешним запросом PKCS#10; во втором случае содержимое сертификата и
  семейство ключа берутся из запроса, а не из полей формы. УЦ подписывает
  только сертификаты своего семейства ключей (`gost` / `rsa` / `ec` /
  `ed25519`), несовместимые сочетания отклоняются до выпуска. Для ГОСТ
  выбирается набор параметров.
- **Профили расширений.** Десять готовых профилей (`server`, `client`,
  `server_client`, `vpn`, `user`, `user_login`, `smartcard_logon`,
  `smime_sign`, `code_signing`, `timestamping`) и любые собственные: KU и
  EKU, basicConstraints, ограничения имён и политик, собственные точки
  распространения, поля из реестра OID (DNS, IP, Email, URI, UPN, СНИЛС, ИНН,
  ОГРН, ОГРНИП и другие). Без профиля доступен свободный режим с произвольными
  расширениями.
- **Точки распространения.** CRL, AIA (caIssuers и OCSP), SIA, freshestCRL и
  issuerAltName задаются для УЦ; профиль может их заменить.
- **Отзыв и CRL.** Причина отзыва записывается в CRL как `reasonCode`. Список
  отзыва выпускается заново при каждом отзыве, а также вручную — для одного УЦ
  или сразу для всех включённых УЦ с публикацией в общий каталог.
- **Продление** сертификата: новый срок и серийный номер при том же запросе и
  том же ключе; исходный сертификат не меняется.
- **Выгрузка.** Сертификат (`.crt`), закрытый ключ, запрос (`.csr`), PEM-файл
  «сертификат + ключ + цепочка», PKCS#12, а также сертификат УЦ и его CRL.
  Контейнер PKCS#12 УЦ шифруется по AES или по ГОСТ (Кузнечик и Магма по
  рекомендациям ТК 26 либо устаревший ГОСТ 28147-89). Для ГОСТ-ключей есть
  формат ТК 26 (`.gost.p12`) — PFX по RFC 9337 и RFC 9548 с шифром Кузнечик
  или Магма.
- **Режимы выпуска.** Можно запретить генерацию ключей на сервере и отдельные
  семейства алгоритмов: запрещённые варианты исчезают из форм, а сервер
  отклоняет их.
- **Обслуживание.** Версия OpenSSL, состояние gost-engine, повторное чтение
  сведений о сертификатах с диска, перевыпуск всех CRL; если установлен
  CryptoPro — состояние провайдера, лицензия и гамма ДСЧ.
- **Два языка интерфейса** — русский (по умолчанию) и английский.

Работа с интерфейсом описана во встроенной справке: она открывается из панели
сразу на разделе, относящемся к текущей странице. Посмотреть панель без
установки можно в [онлайн-демонстрации](#онлайн-демонстрация).

## Профили сертификатов

| Профиль | Key Usage | Extended Key Usage |
|---|---|---|
| `server` | digitalSignature, keyEncipherment, keyAgreement | serverAuth |
| `client` | digitalSignature, keyEncipherment, dataEncipherment, keyAgreement | clientAuth |
| `server_client` | digitalSignature, keyEncipherment | serverAuth, clientAuth |
| `vpn` | digitalSignature | serverAuth, clientAuth |
| `user` | digitalSignature, keyEncipherment | clientAuth, emailProtection |
| `user_login` | digitalSignature, keyEncipherment | clientAuth + OID входа по смарт-карте |
| `smartcard_logon` | digitalSignature | OID входа по смарт-карте |
| `smime_sign` | digitalSignature, nonRepudiation | emailProtection |
| `code_signing` | digitalSignature | codeSigning |
| `timestamping` | digitalSignature | timeStamping (critical) |

## Поддерживаемые алгоритмы

RSA, ECDSA и Ed25519 работают на стандартном OpenSSL без дополнительной
настройки. Для ГОСТ нужен gost-engine; ГОСТ можно отключить, и тогда остаётся
УЦ только на RSA / ECDSA / Ed25519.

- Электронная подпись: RSA (2048 / 4096), ECDSA (P-256, P-384), Ed25519;
  по желанию — ГОСТ Р 34.10-2012 (256 / 512 бит).
- Хеш-функции: SHA-256; по желанию — ГОСТ Р 34.11-2012.
- TLS на входном веб-сервере nginx: обычные наборы шифров RSA/ECDHE, а при
  включённом ГОСТ — также GOST2012-KUZNYECHIK-KUZNYECHIKOMAC и
  GOST2012-MAGMA-MAGMAOMAC.

## Криптопровайдер CryptoPro CSP (дополнительно, сертифицированный ГОСТ)

ГОСТ-операции можно выполнять сертифицированным **CryptoPro CSP** вместо
свободной реализации `openssl + gost-engine`. В этом случае закрытый ключ
создаётся и хранится в контейнере CryptoPro, а через CryptoPro выполняются
генерация ключей, подпись сертификатов корневого и подчинённых УЦ, выпуск
конечных сертификатов (как с генерацией ключа на сервере, так и по внешнему
запросу PKCS#10), продление, выпуск CRL, экспорт в PKCS#12 и импорт
существующего ГОСТ-УЦ из PKCS#12/PFX. Остальные алгоритмы всегда
обрабатываются OpenSSL.

CryptoPro подключается в два этапа: дистрибутив устанавливается в образ **при
сборке** (в репозиторий он не входит), а **при запуске** контейнера провайдер
включается переменной окружения. Команды сборки приведены в
[dev_env/README.md](dev_env/README.md) и [demo/README.md](demo/README.md).

Криптопровайдер выбирается **для каждого УЦ отдельно**, при его создании, и в
дальнейшем не меняется. Поэтому в одной установке могут работать УЦ на
OpenSSL и УЦ на CryptoPro: ранее созданные УЦ остаются на OpenSSL, а
подчинённый УЦ использует провайдер родительского.

На сервере без графического интерфейса CryptoPro нужна **гамма ДСЧ** —
внешний источник случайных данных, который расходуется при каждой генерации
ключа. Гамма загружается на странице «Обслуживание»; там же отображается её
остаток и задаётся лицензия (без собственного серийного номера CryptoPro
работает по встроенной демонстрационной лицензии на 90 дней). Там же можно
сгенерировать тестовую гамму, но **только для испытательного стенда**: при
сертифицированной эксплуатации нужен аппаратный датчик случайных чисел.

### Ограничения криптопровайдера CryptoPro

Ограничения касаются только ГОСТ-УЦ, созданных при включённом CryptoPro. Панель
сообщает о них заранее: недоступные действия скрыты или помечены, а
недопустимая операция отклоняется с понятным сообщением до начала выполнения.

**1. Закрытый ключ нельзя извлечь из контейнера** — в этом и состоит смысл
сертифицированного провайдера. Поэтому недоступны выгрузка ключа в PEM,
PEM-файл «сертификат + ключ + цепочка» и импорт ГОСТ-УЦ из пары PEM-файлов
(для импорта нужен PKCS#12/PFX — ключ из него сразу помещается в контейнер).
Экспорт в PKCS#12 доступен.

**2. PKCS#12 — только в формате CryptoPro.** Такой файл корректно
импортируется в CryptoPro, но выбрать формат ТК 26 (`.gost.p12`) или
ГОСТ-алгоритм шифрования контейнера нельзя: CryptoPro не позволяет задать
шифрование при экспорте. Для УЦ на CryptoPro панель эти варианты не
предлагает.

**3. Поддерживаются не все расширения X.509.**

| Поддерживается | Не поддерживается (выпуск отклоняется) |
|---|---|
| `basicConstraints` (с `pathlen`), `keyUsage`, `extendedKeyUsage` (по имени и по числовому OID), признак критичности | `nameConstraints` |
| `subjectKeyIdentifier`, `authorityKeyIdentifier` (в т. ч. `issuer:always`) | `policyConstraints`, `inhibitAnyPolicy`, `certificatePolicies` |
| `subjectAltName`: DNS, IP, email, URI | `otherName` в SAN |
| `crlDistributionPoints`, `authorityInfoAccess` (caIssuers и OCSP) | произвольные строки из поля «Дополнительные расширения» |
| `subjectInfoAccess` (caRepository), `freshestCRL` | поля реестра OID с размещением «Extension» |
| `issuerAltName`: DNS, IP, email, URI | `issuerAltName` типов `dirName`, `otherName`, `RID` |

Профиль, содержащий что-либо из правого столбца, помечается в редакторе
профилей и в форме выпуска, так что несовместимость видна ещё до заполнения
формы.

В остальном CryptoPro работает так же, как OpenSSL: наборы параметров ГОСТ,
файл `csr.pem` при генерации ключа на сервере, `reasonCode` в CRL, срок
действия CRL, включение SKI/AKI в профиле.

## Ограничения и область применения

- **Одна учётная запись администратора**, задаваемая переменными окружения.
  Ролей, разграничения прав и журнала действий пользователей нет.
- **Только веб-интерфейс.** Протоколов автоматического выпуска (ACME, SCEP,
  EST, CMP) и программного интерфейса для внешних систем нет.
- **Нет OCSP-сервера.** Поля AIA/OCSP лишь записывают адрес в сертификат;
  отвечать по нему должна внешняя служба. Отзыв проверяется по CRL.
- **CRL выпускается по событию, а не по расписанию** — при отзыве и по
  кнопке. Планировщика и уведомлений об истечении сертификатов нет; на
  обзорной панели показан только список сертификатов с истекающим сроком.
- **Аппаратные носители и HSM (PKCS#11) не поддерживаются.** Из
  сертифицированных способов хранения ключа доступен только программный
  контейнер CryptoPro CSP.
- **Данные хранятся в локальном каталоге** одного сервера. Кластеризация и
  репликация не предусмотрены. PostgreSQL хранит только сведения для поиска и
  списков, а основной источник данных — файлы на диске.
- **Готовые окружения из репозитория предназначены для стенда.** Панель в них
  работает на встроенном отладочном сервере Django, с самоподписанным
  сертификатом TLS и паролем `admin` по умолчанию. Для эксплуатации нужны
  WSGI-сервер, собственный `DJANGO_SECRET_KEY`, настоящие сертификаты для
  nginx и смена учётных данных.
- **Резервное копирование.** Ключи УЦ на OpenSSL лежат в каталоге хранилища
  вместе с сертификатами, а ключи УЦ на CryptoPro — отдельно, в контейнерах
  провайдера. Копировать нужно оба тома одновременно: УЦ на CryptoPro,
  восстановленный только из каталога хранилища, ничего подписать не сможет.
  Перечень томов приведён в README окружений.
- **ГОСТ через gost-engine — свободная, несертифицированная реализация.** Если
  нужна сертифицированная криптография, используйте CryptoPro CSP с
  описанными выше ограничениями.
