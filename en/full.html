Extended edition · on top of the open one

An enterprise CA for deploying PKI // RBAC · requests · Windows auto-enrol · PAT API · TOTP · OID/policy registries

The open edition of OwnCA is a CA with a single administrator account: issue and revoke X.509 certificates, CRLs, extension profiles, PEM and PKCS#12 export. The extended edition turns it into the foundation for company-wide PKI: permission-based access, sign-in with Active Directory and 2FA with privacyIDEA, automatic Windows certificate enrolment by Group Policy, a request queue with operator approval, API token access, second-factor issuance (TOTP), dedicated Custom OID and Certificate Policy registries, plus qualified GOST profiles (Russian QES). Below is only what the open edition does not have.

// access & roles

From a single operator to enterprise PKI with RBAC.

Permission-based roles

Access is driven by a catalog of functional-area permissions grouped into roles and granted per account. The permission applies in the API too.

User & role management

Assign one or more roles per account (effective permissions are the union).

Assigned CAs

An operator has access only to the CA profiles explicitly assigned to them. An attempt to issue through an unassigned CA is refused.

Password Policy

A dedicated page in the System section with password-complexity rules for accounts — absent in the open edition, where System is limited to Configuration and Maintenance.

Allowed certificate profiles

Each CA gets its own list of allowed profiles: in the issue form the operator sees only those, and issuance with an unbound profile is rejected.

User action audit log

The log records account actions — sign-in, certificate issuance and revocation, CRL regeneration, changes to profiles, registries and CA settings — tied to the user, time and IP. Available to admins for incident review and oversight.

// self-service portal

Active Directory sign-in, TOTP and password self-service.

Sign-in via privacyIDEA + Active Directory

A user@domain login is authenticated against Active Directory with TOTP verification through privacyIDEA.

First-login TOTP enrolment

An AD user with no 2FA set up is guided through TOTP self-enrolment. The next sign-in then asks for the second factor.

Password change in Active Directory

Directory users can change their own AD password themselves.

Password expiry & must-change

At login OwnCA shows an "expires soon" warning, and an account that must change its password is offered a password-change form right away.

Force change on next login

Flag a new or reset AD account as required to change its password on next sign-in — the user cannot work until a new password that meets the AD policy is set.

// Active Directory auto-enrolment

Certificates for Windows — automatic, by Group Policy.

Windows certificate auto-enrolment

Domain computers and users get certificates automatically through Group Policy (GPO) — with no manual steps and no admin ticket.

Automatic renewal

Certificates renew on their own before they expire — the user does nothing and work is never interrupted.

Publish to the directory

Issued certificates are published automatically into users' Active Directory accounts and made available across the domain.

Domain trust for your CA

The CA certificates and revocation lists are published to the domain so every computer trusts what you issue — no manual install on each machine.

Sign-on with the domain account

On the domain network enrolment runs off the current Windows session, without re-entering a username and password.

Enrolment templates & control

Admins define the certificate templates clients can use, optionally route requests for operator approval, and cap the number of certificates per user.

// requests & approval

Users request — operators approve and issue.

User-submitted requests

The user submits a request: CN, key algorithm, SAN, an optional PKCS#10 request and a comment. CA and profile selection are hidden — the operator assigns them at approval.

Operator queue

Operators and admins see the request queue filtered by status (pending / approved / rejected). A pending request opens as the full issue form, prefilled with the request data.

PKCS#10 import in the request form

PKCS#10 (CSR) import with field auto-fill and a loading banner works in the user request too — identical to the operator page.

// API access

Personal Access Token — automation without a browser.

API access is off by default and is enabled by an admin for a specific user. The user issues their own token in their profile (one per account, stored as a hash, plaintext shown exactly once). Requests carry an Authorization: Bearer ownca_pat_… header; the token inherits its owner's role and keeps their IP restrictions.

API ACCESS panel

An admin enables API for a user with a single toggle. Disabling it automatically revokes the user's issued token.

Generate / Regenerate / Revoke

The user manages their own token from their profile. A short prefix stays visible in the UI for identification, and the last-used time updates on every call.

$ curlPAT API
# list available CAs with a Personal Access Token $ curl -H "Authorization: Bearer ownca_pat_…" \ https://ca.ownca.example/cas/ # regenerate the CRL for a specific CA $ curl -X POST -H "Authorization: Bearer ownca_pat_…" \ https://ca.ownca.example/cas/<uuid>/crl/generate/ # response {"status":"ok","crl_number":1007, "download_url":"/crls/<uuid>.crl"}
// issuance security

OTP and network restrictions.

OTP-gated issuance and TOTP in the profile

In the settings, an admin can turn on mandatory OTP. When set, selecting that CA in the issue and approval forms reveals an OTP code field, and issuance without a valid code is refused. The user sets up and confirms TOTP (for example, with an authenticator app) in their profile.

Per-user IP restrictions

An allowed-subnet list is set per user and applies to both browser sessions and API calls — requests outside the allowed subnets are rejected regardless of token validity.

Strict "profile+form > request" priority

Extensions from an imported PKCS#10 request (basicConstraints, KU, EKU, SAN) are dropped by force. Only the Subject DN from the request, SAN from the form and the selected profile's extensions land — a "hostile" request with CA:TRUE does not leak through.

// registries & qualified profiles

Dedicated pages to manage OIDs, policies and QES profiles.

Custom OIDs registry

A dedicated page (admin) manages the OID-field registry: OID, display name, ASN.1 type and where the value is placed. Built-in set: DNS, IP, Email, URI, UPN, SNILS, INN, OGRN, OGRNIP and others.

Certificate Policies registry

A dedicated page (admin) manages policies for the certificatePolicies extension: OID, a link to the CPS document and notice text. Built-in policies: QES individual / org / sole proprietor.

Personal theme

In the user profile — a choice of three theme families (Default / Dark / Warm) with a hue slider; the setting is kept per user.
