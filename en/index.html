Self-hosted · Docker · EasyRSA, but a web panel · CryptoPro CSP (optional)

Your EasyRSA scripts, as a web panel // init-pki · build-ca · build-server-full · sign-req · gen-crl

OwnCA is a self-hosted web panel for a Certificate Authority — a replacement for the pile of EasyRSA and openssl ca shell scripts. It does the same job: stands up roots and intermediates, issues and revokes X.509 certificates, keeps CRLs fresh, exports keys and certificates in PEM and PKCS#12 — only from a browser instead of a terminal.

It runs on stock OpenSSL with RSA, ECDSA and Ed25519. GOST R 34.10-2012 support is strictly opt-in: with GOST switched off you get an ordinary CA on an unpatched OpenSSL with no engine to install. GOST keys also offer the TK-26 format (.gost.p12) — a PFX per RFC 9337 and RFC 9548, the dialect CryptoPro and other Russian providers actually read. Where certified cryptography is required, the GOST path moves onto CryptoPro CSP — per CA, not per installation.

// what's inside

Everything your EasyRSA wrapper does — without the shell scripts.

AUTHORITIES

Roots & intermediates

The init-pki / build-ca step, made clickable: key and self-signed certificate generation, signing an intermediate with its parent, and importing an existing CA (a certificate with its private key, or a PKCS#12/PFX container) to keep signing with it. You choose the key algorithm, Subject DN, validity period and path length (pathlen). An intermediate is created in its parent's key family — GOST and RSA never mix within one chain.

ISSUANCE

Unified Cert Issue form

One form replaces the build-server-full / build-client-full / sign-req incantations. The key is either generated server-side or arrives with an external PKCS#10 request — in the latter case the certificate's contents and its key family are taken from the request itself, not from the form fields. A CA only signs certificates of its own key family (gost / rsa / ec / ed25519); incompatible combinations are rejected before issuance. GOST keys get a selectable parameter set.

PROFILES

Extension profiles

Ten seeded ones (server, client, server_client, vpn, user, user_login, smartcard_logon, smime_sign, code_signing, timestamping) plus any of your own: KU and EKU, basicConstraints, name and policy constraints, distribution-point overrides, and bound OID fields from the registry (DNS, IP, Email, URI, UPN, SNILS, INN, OGRN, OGRNIP and others). Without a profile there is a free-form mode with arbitrary extensions.

DISTRIBUTION

Distribution points, per CA

CRL, AIA (caIssuers and OCSP), SIA, freshestCRL and issuerAltName are set per CA and can be overridden by a profile — and are embedded in every leaf the CA signs.

REVOCATION

Revocation and CRLs

The revocation reason reaches the CRL as reasonCode. The list is reissued automatically on every revocation, manually on demand, and for every enabled CA at once into the distribution directory.

RENEWAL

Same key, new validity

Renewal of a certificate under a new validity period and serial number from the same request and the same key; the original is left untouched, and the "renewed from" link stays visible on the certificate page.

EXPORT

Standard PFX, GOST optional

The certificate (.crt), private key, request (.csr), a PEM file holding certificate + key + chain, PKCS#12, plus the CA certificate and its CRL. A CA container is encrypted with standard AES or a GOST suite (Kuznyechik and Magma per TK-26, or legacy GOST 28147-89). GOST keys also offer the TK-26 format (.gost.p12) — a PFX per RFC 9337 and RFC 9548; turn GOST off and you never touch it.

ISSUANCE MODES

Turn off what you don't want

Server-side key generation, individual algorithm families, .gost.p12 export and free-form issuance can each be disabled — the corresponding options then disappear from the forms and are rejected server-side.

NGINX TLS

Plain TLS, GOST on demand

The bundled nginx serves the regular RSA/ECDHE suites out of the box. Enable GOST and it also terminates GOST2012-KUZNYECHIK-KUZNYECHIKOMAC on the same socket; leave it off and it's an ordinary TLS endpoint on stock OpenSSL.

OPS

State lives in files

CA material, issued certs and CRLs are flat files under OWNCA_STORAGE_DIR/. PostgreSQL holds only the metadata index, while the files on disk are the source of truth — you can tar the storage dir and move a CA between hosts.

MAINTENANCE

Versions, reindex, every CRL

openssl version, gost-engine status, metadata reindex from disk, rebuild of every CRL; on a build with CryptoPro — provider status, licence and DRBG gamma.

WEBHELP

Contextual and built in

Working with the interface is covered by the built-in contextual help, opened straight from the panel and always matching the current page. Two languages — Russian (default) and English — for both the UI and the help.

Standard algorithms work on stock OpenSSL out of the box. GOST requires gost-engine and can be switched off, leaving a clean RSA / ECDSA / Ed25519 CA. Frontend TLS runs the ordinary RSA/ECDHE suites, plus GOST2012-KUZNYECHIK-KUZNYECHIKOMAC and GOST2012-MAGMA-MAGMAOMAC when GOST is enabled. Where a certified implementation is required, GOST moves onto CryptoPro CSP.

// certified GOST

Same screens — but the key is born and stays inside CryptoPro CSP.

The CA's GOST operations can run on the certified CryptoPro CSP instead of the free openssl + gost-engine. The private key is then born and stays inside a provider container: key generation, root self-signing, intermediate CA signing, end-entity issuance (both server-side key generation and external CSRs), renewal, CRL generation, PKCS#12 export and import of an existing GOST CA from PKCS#12/PFX all go through CryptoPro. Non-GOST algorithms always stay on openssl.

KEY

The private key is non-exportable

That is the whole point of the certified backend: the private key is born and stays in a provider container. So such a CA has no PEM key download, no "certificate + key + chain" PEM bundle and no PEM-pair import — PKCS#12 export still works.

SCOPE

Per CA, not per installation

The backend is fixed when the CA is created and never changes. openssl-backed and CryptoPro-backed CAs coexist in one deployment, pre-existing CAs stay on openssl, and an intermediate inherits its parent's backend.

STAND

DRBG gamma and licence in the UI

On a headless server the provider needs DRBG gamma — external entropy consumed on every key generation. You upload it on the Maintenance page, which also shows the remaining amount and manages the licence (without a serial of your own, CryptoPro runs on its built-in 90-day demo licence). Test gamma can be generated right there, but for a test rig only — certified operation requires a hardware source.

CryptoPro backend limitations

The limitations apply only to GOST CAs created while CryptoPro was enabled. None of them is silent: anything unsupported is either hidden in the UI, flagged up front, or refused with an explicit error before the operation starts.

// honest about the edges

What OwnCA does not do.

This is a compact CA for your own needs, not an enterprise PKI platform. Better to learn the limits here than on day three of running it.

A single administrator account, provisioned from environment variables. There are no roles, no permission separation, and no per-user audit trail.
Web UI only. No automation protocols (ACME, SCEP, EST, CMP) and no external issuance API.
No OCSP responder. The AIA/OCSP fields merely write a URL into the certificate; something else has to answer on it. Revocation checking is via CRL.
CRLs are refreshed on events, not on a schedule — on revocation and on demand. There is no scheduler and no expiry notifications; the dashboard only lists certificates that are about to expire.
No hardware tokens or HSMs (PKCS#11). The only certified key storage option is the software CryptoPro CSP container.
Storage is a local directory of a single instance. Clustering and replication are out of scope; PostgreSQL holds only the metadata index, while the files on disk are the source of truth.
The environments shipped here are test rigs. The panel runs on Django's development server with a self-signed TLS certificate and the default admin password. Production use needs a proper WSGI server, your own DJANGO_SECRET_KEY, real frontend certificates, and changed credentials.
Two backups, not one. For an openssl-backed CA the keys sit in the storage directory next to the certificates; for a CryptoPro-backed CA they live separately, in provider containers. Both volumes must be backed up, and consistently: a CryptoPro CA restored from the storage directory alone will not be able to sign anything.
GOST on gost-engine is a free, uncertified implementation. If certified cryptography is required, the CryptoPro CSP backend is the answer — with the limitations described above.
// run it in 90 seconds

Two compose files. Pick your poison.

dev_env — built from source, code mounted into the container, live-reload. For development and debugging. demo — pre-built images; the stack moves to an air-gapped host as a single archive.

CryptoPro is off by default and enablement is two-level: the distribution must be staged into the image build (it is not part of the repository), and the backend is then switched on at container start through an environment variable. Without that you get an ordinary openssl + gost-engine image.
